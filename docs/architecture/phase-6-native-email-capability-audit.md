## Attachment Transport Foundation

### Editor And Approval Integration

Marketing Email's Add file picker now supports new uploads as well as existing tenant files. Uploads pass a dedicated private endpoint requiring tenant administrator, native marketing edit/create and attachment-field permissions. Encoded payload length, filename, extension/MIME pairing and actual contents are checked before reusing the native tenant library storage path. The existing library and Cloudflare R2 ownership remain authoritative; no new asset table or public URL is introduced. The shared picker receives marketing-only extension and 5 MiB limits without narrowing other CRM file workflows. Uploading does not approve or send a file: saving still makes native template copies and approval snapshots. Save is disabled while uploading; responses from closed or replaced drafts cannot attach to the new draft. Browser tests cover upload payloads, client rejection, busy state and stale responses; runtime tests cover invalid payloads/types/sizes, non-admin rejection and tenant-owned upload/application/restoration. Closing without saving leaves the uploaded file available in the tenant library.

The editor now selects existing files through the tenant file library, rejects duplicate selections and checks file-size/count limits. Native attachment copying keeps library originals intact while giving each template its own relationship records. Saving validates tenant/service ownership, native Attachment read permission, EmailTemplate attachment field permission, storage bytes, MIME type and limits. Saved-version audit events capture file ID, filename, type, size and SHA-256; approval refuses files changed since saving. Restoring a content version checks its file manifest and creates a fresh draft with native attachment copies. No schema migration is required.

`TenantMarketingAttachmentTest.php` verifies the native relationship, two-tenant rejection, approval-time tampering checks, post-approval checksum verification and version restoration with temporary fixture files cleaned up. Real-customer delivery is not tested.

`DeliveryRequest` now accepts validated `DeliveryAttachment` MIME parts. The Postal adapter submits their filename, MIME type and base64-encoded bytes through the existing send API, without making tenant storage URLs public. Limits are 5 MiB per file, 10 MiB combined and 10 files. Supported extensions/types are PDF, TXT, CSV, JPEG, PNG, GIF and WebP; content detection, UTF-8 filenames, path/control-character rejection and nonempty-content checks run before transport. This is not a malware-scanning guarantee.

`PostalAttachmentAcceptanceTest.php` verifies a real HTTPS submission and SMTP capture, including attachment name, MIME type and content in the received message. This is a transport-layer test, not a customer campaign acceptance test. Editor selection, permission checks, manifests, restoration and governed dispatch are connected as described above. Attachment-bearing reusable-template selection uses the governed loading and draft snapshot path described below. No new schema or public file endpoint has been added. ## Delivery readiness boundary

Migration `0063` adds tenant/service-owned provider configuration, sending-domain readiness, suppression and immutable delivery-event storage. Provider credentials use the existing encrypted managed-secret store and are never returned to the browser. A tenant is delivery-ready only after a credential exists and at least one exact sending domain passes ownership, SPF, DKIM, DMARC and custom return-path checks.

Postal remains responsible for accepting and delivering messages, retrying temporary failures and monitoring its configured domains. Nexa owns campaign consent, tenant limits, scheduling authorization, callback idempotency, canonical customer events and suppression decisions. Postal documents that its current HTTP API is intentionally limited to message operations, while sending domains and their DNS records are administered in Postal and checked by its workers: https://docs.postalserver.io/developer/api/ and https://docs.postalserver.io/features/sending-domains/.

Migration `0064` adds the native-queue-to-provider message map and monthly usage ledger. The public callback uses a 48-character one-time token whose SHA-256 hash is stored per tenant and service; administrators can rotate the URL, and repeated provider events are idempotent. Hard bounces and complaints enter the tenant suppression list automatically.

`MarketingDeliveryProvider` is the transport boundary. `PostalDeliveryProvider` retrieves the tenant's encrypted API key only at runtime and submits through Postal's HTTPS message API. It does not select recipients, bypass consent, construct a second campaign queue or own scheduling. The governed dispatcher must continue to select and render native `EmailQueueItem` records before invoking this adapter.

## Governed dispatch boundary

Approved emails can be scheduled only when their campaign is active, their sender domain is verified and the tenant has sufficient monthly capacity. `ProcessMarketingDelivery` runs once per minute inside each tenant's scheduled-job context. It creates native `EmailQueueItem` records from governed campaign enrollments and renders the native `EmailTemplate` for each Contact.

Eligibility is checked again immediately before submission. Withdrawn or expired consent, contact and channel do-not-contact controls, target-list opt-out, native invalid/opted-out email flags and active provider suppressions all prevent delivery. Monthly capacity is locked and reserved before the external request. A delivery-message record is created before calling Postal so concurrent workers cannot submit the same queue item twice. Native Mass Email statuses use `Nexa Scheduled` and `Nexa Sending` while Postal owns transport, preventing the stock SMTP worker from racing the governed dispatcher.

## Callback reconciliation checks

The receiver accepts Postal's event envelope with a nested `payload` as well as the direct payload format. Callback UUIDs provide retry idempotency when present; the fallback identity includes click URL and tracking token. Engagement events cannot reset delivery status, and late delivery/defer notifications cannot overwrite terminal failures. Monthly delivery counters advance only for a matched message status transition, so unmatched callbacks and repeated notifications cannot inflate totals. Postal API response parsing supports recipient-keyed message results.

Local database acceptance covers nested payloads, retries, opens/clicks after delivery, delayed events arriving after delivery, and repeated delivery notifications. Callback message tokens also resolve differences between Postal's API and webhook message identifiers; the stored recipient must match before a known message can be reconciled.

Unmatched callbacks are retained for investigation but do not create customer activity.

## Interrupted submission guard

Paused emails now expose a tenant-administrator submission-review dialog. The authenticated API requires native MassEmail scope and record edit access, row-locks the profile/message/native queue, and requires provider evidence. Confirmed acceptance links an exact provider message ID and reconciles the queue without another send or allowance charge. Confirmed non-acceptance is allowed only before any provider acceptance ID exists; it marks the held item failed and releases one reservation from its original calendar month. Repeated review is rejected and records no second release. Evidence, outcome and actor are appended to the existing marketing audit events. Review never resumes a campaign or resets an item to Pending. This is an administrator-attested evidence workflow, not automated Postal log verification. Automated provider inspection and public external-delivery acceptance remain pending.

The transport adapter now distinguishes explicit structured 4xx rejections from uncertain submission outcomes. Timeouts, interrupted/oversized responses, malformed responses, server errors and acceptance without a message ID do not prove non-acceptance. Such outcomes immediately pause the governed profile, retain the native queue hold and monthly reservation, and record one review-required event. Unexpected persistence errors after calling the provider receive the same conservative hold. Explicit rejections and preflight failures retain the existing failure/release behavior. Runtime tests verify reservation preservation, repeated-event idempotency and foreign-tenant rejection; focused tests cover response classification. Resolution uses the evidence-review workflow above; automatic resend is not authorized.

Completion waits for both Pending and Sending native queue items. The tenant worker pauses a sending profile when a submitting message has had no update for 15 minutes, keeps its monthly reservation and records one `submission_review_required` audit event. The native MassEmail becomes `Nexa Paused`, preventing the stock SMTP worker from sending it. Recovery does not clear the queue or automatically resend: an interrupted worker may have submitted to Postal before losing its response. Active, unmarked submissions cannot be manually resolved until they become stale or uncertain. Transactional tests cover active submissions, stale pauses, repeated workers and cross-tenant isolation. No schema migration is required.
